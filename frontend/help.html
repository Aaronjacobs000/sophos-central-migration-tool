Help and prerequisites

What the tool does, what it needs before you start, and the limits to know about.

What this tool does

It connects to two Sophos Fusion (formerly Sophos Central) tenants, a source and a destination, and moves configuration and devices between them through the public Sophos APIs. It does not copy the whole tenant. You choose what moves and when, and every change is logged.

  • Endpoint policies: list, compare settings, and clone or overwrite on the destination.
  • Endpoint groups: mirror by name and description. Membership is not copied (see below).
  • Exclusions and allow and block lists: copy scanning exclusions, allowed items and blocked items.
  • Device migration: the two-tenant migration flow. Devices keep their identity and check in to the destination the next time they are online.

Before you start

  1. Sign in to the source Sophos Fusion tenant as a Super Admin.
  2. Open Global Settings > API Credentials and add a credential with the Super Admin role. Copy the Client ID and Client Secret.
  3. Do the same in the destination tenant.
  4. This tool only uses tenant-scoped API credentials. Partner or organization credentials are not supported.
  5. On the destination tenant, confirm Device Migration is enabled in Global Settings > Device Migration. The destination must allow incoming migrations within a set time window.

The 14-day window

Sophos's device migration needs every selected device to check in within 14 days for the move to land. The tool checks this twice:

  • Devices with a stale last-seen time are greyed out and cannot be selected.
  • The server runs a preflight check before creating jobs and refuses to start if any selected device is outside the window.

If a device does not check in during the window, its entry stays pending on Sophos's side and you will need to queue it again later.

Moving devices

  1. Pick devices on the Endpoints page. Stale ones are blocked.
  2. Press Migrate to open the migration form.
  3. Run a dry run to see the plan without any upstream writes.
  4. Name the job, tick the 14-day acknowledgement and create the jobs. The tool creates a receiving job on the destination, then triggers the sending job on the source with the receiver's handshake token.
  5. The job page follows a server-side event stream and shows each device's status as it moves.

Group membership

Mirroring an endpoint group copies its name and description only. Member IDs from the source mean nothing in the destination, so they are left out. Devices reconstitute group membership on the destination side based on its policies after they migrate.

Dry runs

Every migration action (policies, groups, exclusions and device migrations) supports a dry run that returns the plan the server would carry out without touching the destination. Use it the first few times until you are comfortable with what gets created.

Audit log

Every change to either tenant is written as a JSON line to data/audit.log with a timestamp, request ID, side, resource ID, and the result or error. Keep it for change control.

Security

  • The server only listens on 127.0.0.1 and is not reachable from the network.
  • Credentials are stored in .env at the repo root, which .gitignore excludes. Do not back it up to cloud drives, and run the tool on a workstation with full-disk encryption.
  • The API never returns secrets; the credentials page shows masked values.
  • Destructive actions (delete, overwrite, cancel migration) ask for confirmation.
