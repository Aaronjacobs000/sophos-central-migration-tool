Help & prerequisites

Everything you need to know to use this tool safely.

What this tool does

Connects to two Sophos Fusion (formerly Sophos Central) tenants, a source and a destination — and lets you migrate configuration and devices between them via the official Sophos APIs. It does not replicate the entire tenant; it gives you targeted, auditable control over what moves and when.

  • Endpoint policies — list, deep-diff, and clone (or overwrite) on the destination.
  • Endpoint groups — mirror by name and metadata. Membership is not copied (see below).
  • Exclusions and allow/block lists — copy scanning exclusions, allowed items, and blocked items.
  • Device migration — uses the official two-tenant migration flow. Devices keep their identity and check in to the destination on next online.

Before you start

  1. Sign in to the source Sophos Fusion tenant as a Super Admin.
  2. Open Global Settings → API Credentials and click Add Credential. Pick a Super Admin role and copy the Client ID and Client Secret.
  3. Repeat the same steps in the destination tenant.
  4. This tool only uses tenant-scoped API credentials — partner or organization credentials are not supported.
  5. On the destination tenant, confirm Device Migration is enabled in Global Settings → Device Migration. The destination must allow incoming migrations within a defined time window.

The 14-day window

Sophos's device migration flow requires every selected endpoint to check in within 14 days for the migration to land. This tool enforces it twice:

  • Endpoints with stale lastSeenAt are greyed out and cannot be selected.
  • The server runs a preflight check before creating jobs and refuses to start if any selected endpoint is outside the window.

If a device fails to check in during the window, the migration entry stays pending on Sophos's side and you'll need to re-queue it later.

Migration workflow (devices)

  1. Pick endpoints on the Endpoints page. Stale ones are blocked.
  2. Click Start migration to go to the migration form.
  3. Optionally run a dry run to see what will happen, with no upstream writes.
  4. When ready, give the job a name, tick the 14-day acknowledgement, and create the migration jobs. The tool calls Sophos to create a receiving job on the destination tenant, then a sending job on the source tenant with the receiver's handshake token.
  5. The job detail page subscribes to a server-side event stream and shows live status as devices migrate.

Group membership caveat

When you mirror an endpoint group, only the name and metadata are copied. The list of member endpoint IDs is meaningless in the destination tenant, so it is intentionally omitted. Devices reconstitute group membership on the destination side based on its policies after they migrate.

Dry-run mode

Every migration action — policies, groups, exclusions, and device migrations — supports a dry-run that returns the plan the server would execute without touching the destination tenant. Use it the first few times until you are comfortable with what gets created.

Audit log

Every mutation against either tenant is recorded as a JSON line in data/audit.log with a timestamp, request ID, side, resource ID, and either the success detail or the error message. Keep it for change-control records.

Security

  • The server only listens on 127.0.0.1. It is not reachable from the network.
  • Credentials are stored in .env at the repo root. The file is in .gitignore. Do not back it up to cloud drives. Run on a workstation with full-disk encryption.
  • Secrets are never returned by the API; the credentials page shows masked values.
  • Destructive actions (delete, overwrite, cancel migration) require an explicit confirmation.
